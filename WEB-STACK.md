# Web stack catalogue

Canonical reference for every language, library, framework, platform and system that can appear in a web or app project here. One row per thing: what it is, which slot it occupies, and whether it belongs in Douglas's stack.

`DESIGN.md` is the authority for taste and anti-default discipline. This file is the authority for *what each thing is*. Where the two touch, `DESIGN.md` wins.

## How to read this

The stack is a set of **slots**. Each slot answers one question. Some slots hold exactly one occupant; some hold as many as you like. Nothing conflicts unless two things want the same slot.

| Column | Meaning |
|---|---|
| **Slot** | Which question it answers |
| **Verdict** | `USE` — the default here · `OK` — fine when a project needs it · `SKIP` — actively avoid · `KNOW` — you will meet it, you do not choose it |

Verdicts are for Douglas's context: solo work, agent-written code, local tools plus a few deployed apps. They are not universal judgments.

## 1. Languages

The only things a browser parses are HTML, CSS and JavaScript. Everything else in this document turns into those three before it reaches a screen, or runs on a server instead.

| Name | What it is | Slot | Verdict |
|---|---|---|---|
| **HTML** | Declares what content exists and what kind of thing each piece is. No logic, no appearance. | Content | USE |
| **CSS** | Declares how existing content looks. No logic. | Appearance | USE |
| **JavaScript** | A general-purpose programming language. The only one browsers run. Does arithmetic, decisions, loops, network requests, and changes the page after load. | Behaviour | USE |
| **TypeScript** | JavaScript plus written-down declarations of what shape each piece of data has. A compile step checks those declarations and then deletes them, emitting plain JavaScript. Absent at runtime. | Type checking | USE |
| **JSX / TSX** | A syntax extension letting you write HTML-shaped markup inside JavaScript/TypeScript. Compiles to function calls. Not a language. | Syntax | KNOW |
| **Python** | General-purpose language used here for tooling, data work and ML. Not run by browsers. | Backend / tooling | USE |
| **PowerShell** | The shell every harness script is written in on this machine. | Automation | USE |
| **SQL** | Query language for relational databases. | Data | USE |
| **WebAssembly** | A compiled binary format browsers can run alongside JavaScript, for compute-heavy work. | Behaviour (specialist) | KNOW |

## 4. UI libraries

These answer: *how do I keep what is on screen in agreement with my data?*

Without one, you change the page by locating each element and setting its properties yourself — and every piece of state has to be manually written into every place that displays it. Miss one write and the screen shows something the data does not say. A UI library removes that class of mistake by making the screen a function of the data.

| Name | What it is | Slot | Verdict |
|---|---|---|---|
| **React** | Library. You write functions ("components") that return markup describing the screen for a given set of data. When the data changes, React recomputes and applies the minimum set of changes. You never locate or mutate elements. Largest ecosystem by a wide margin. | UI structure | USE |
| **Vue** | Same job, template-file oriented, gentler learning curve. | UI structure | SKIP (one per app; React chosen) |
| **Svelte** | Same job, compiles away so no library ships. Less code to write. Smaller parts ecosystem. | UI structure | SKIP (same reason) |
| **Solid** | Same job, finer-grained updates, React-like syntax. Small ecosystem. | UI structure | SKIP |
| **Preact** | React-compatible, much smaller. For size-critical work. | UI structure | OK |
| **HTMX** | Opposite approach: server returns HTML fragments, tiny script swaps them in. No components, no build step. | UI structure | OK for server-rendered tools |
| **Alpine.js** | Small sprinkles of interactivity via HTML attributes. No build step. | UI structure | OK for one-off pages |
| **Lit / Web Components** | Browser-native component standard. Framework-independent. | UI structure | KNOW |

**One per app.** These are mutually exclusive rendering engines.

**Do you need one?** If the screen mostly displays fixed content, no. Past roughly three elements that must stay consistent with the same piece of changing state, yes.

## 5. Frameworks

A framework owns the structure and the build, and calls your files. The practical test: **does a file you wrote start the application?** With a library, yes — you wrote the entry point. With a framework, there is no entry point you wrote; you place files at paths it defines and it starts itself.

| **Remix / React Router 7** | React framework centred on web standards and forms. | Framework | OK |
| **TanStack Start** | Newer React framework, type-safe routing throughout. | Framework | OK |
| **SvelteKit** | Svelte's framework. | Framework | SKIP |
| **Nuxt** | Vue's framework. | Framework | SKIP |
| **Gatsby** | Older React static-site framework. | Framework | SKIP |
| **Express** | Minimal Node HTTP server framework. The old default. | Backend framework | OK |
| **Fastify** | Faster Express alternative with schema validation. | Backend framework | OK |
| **Hono** | Very small, fast, runs on Node, Bun, Cloudflare Workers, Deno. | Backend framework | USE for standalone APIs |
| **NestJS** | Heavily structured, decorator-based, Angular-like. Large-team oriented. | Backend framework | SKIP |

## 8. Headless component primitives

These give working, accessible component *behaviour* with no appearance at all. They exist because the hard part of a dropdown — focus movement, arrow keys, Escape, click-outside, scroll locking, collision-aware positioning, correct ARIA roles — is several hundred lines of difficult code that is identical on every website ever built, while the *look* is the only part anyone wants to be theirs.

| Name | What it is | Slot | Verdict |
|---|---|---|---|
| **Radix UI** | ~30 unstyled, accessible primitives. The de facto standard. What shadcn/ui is built on. | Primitives | USE (arrives with shadcn) |
| **Base UI** | Radix's successor from the same lineage. shadcn is migrating toward it. | Primitives | KNOW |
| **Headless UI** | Tailwind Labs' equivalent. Smaller set. | Primitives | OK |
| **React Aria** | Adobe's set. The most rigorous accessibility, more work to use. | Primitives | OK |
| **Ark UI** | Framework-agnostic primitives built on state machines. | Primitives | OK |

**One primitive layer per app.** Use whichever your component registry installs.

## 9. Component registries

The defining property: **`npx shadcn add button` writes a file into your project.** It does not install a dependency. `components/ui/button.tsx` is ~50 lines of readable Radix + Tailwind, committed to your repo, yours to edit.

That matters concretely because `node_modules/` cannot be meaningfully edited — edits there are wiped on install and the files are minified machine output. So **"lives in my repo" and "an agent can change it" are the same property.** The copy-in model is what makes components agent-editable.

It also explains the abundance: with no package to version, no API to design and no breaking changes to manage, publishing components became trivial, so dozens of people did — and they all interoperate, because every one is just Tailwind classes plus Radix behaviour dropped into a folder.

## Slot occupancy rules

**Exactly one:** language, UI library, framework, styling system, primitive layer, ORM, hosting target.

**As many as useful:** component registries, animation libraries, chart libraries, icon sets, testing tools, reference sources, agent skills.

**Known conflicts:** Tailwind against MUI / Chakra / Mantine / Ant / Bootstrap · shadcn against any full component framework · React against Vue / Svelte / Solid · Next.js against Astro in one app · two primitive layers at once.

**Why the compatible things are compatible:** they occupy non-overlapping concerns. Radix does behaviour and no styling. Tailwind does styling and no behaviour. Framer Motion does motion and neither. Nothing overlaps, so nothing fights. MUI conflicts with Tailwind precisely because MUI wants behaviour *and* styling *and* theming — three slots, two already taken.
